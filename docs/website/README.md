# Maintain the gvy website

The site uses Astro, Starlight, and Bun and deploys to GitHub Pages at `/gvy/`. Run these commands from this directory:

```bash
bun install --frozen-lockfile
bun run generate
bun run validate
bun run dev
```

`validate` checks formatting, projection regression tests, generated reference drift, Astro types, the production build,
and built links, assets, fragments, and compatibility URLs. Production search is generated by Pagefind during the build.
To test search locally, run `bun run preview` after building; stop the owned background preview with
`bunx astro preview stop` (or press Ctrl-C for a foreground server).

## Source of truth

[The source-to-page map](content-map.mjs) explicitly assigns repository Markdown to routes. Edit those source files, not
the ignored `.md` projections under `src/content/docs`. The homepage remains hand-authored MDX. Generated pages retain
the source title's anchor, convert repository links to website routes when mapped, link other repository files to
GitHub, convert GitHub alerts to readable labeled quotations, and point **Edit page** to the canonical Markdown.

The projector parses Markdown as an AST. It rejects unsupported HTML and ambiguous heading conversions rather than
silently changing their meaning. Code fences remain literal. When introducing new Markdown constructs, extend the
projection tests before adding the content. The old published URLs and fragments are recorded in
[route-inventory.json](route-inventory.json); the build verifies that they still exist.

The [settings](../user/reference-settings.md) and [commands](../user/reference-commands.md) references are generated
from two manifests. The stable snapshot is extracted from the published VSIX and verified against the release checksum;
the development table reads `editors/code/package.json` from the checkout. `bun run generate --check` checks reference
drift; `bun run generate` refreshes it. Manifest presence describes configuration declarations, not tested runtime
support. Keep the [feature support matrix](../lsp/feature-support.md) provisional until the quality harness supplies the
scorecard required by [#1550](https://github.com/albertocavalcante/gvy/issues/1550).

## Release refresh

Before changing the stable edition:

1. Verify the new tagged VSIX, standalone JAR, checksums, and embedded server bytes. Record the actual server version
   and source revision. Retain the v0.5.4 bundled-server warning until a corrected stable release is verified
   ([#1751](https://github.com/albertocavalcante/gvy/issues/1751)).
2. Update direct download URLs in the repository README and installation guide together with distribution pins through
   [#1675](https://github.com/albertocavalcante/gvy/issues/1675). Never overwrite a released artifact.
3. Extract `extension/package.json` from the verified VSIX. Replace the stable snapshot and its version/hash/provenance
   in the generator through a reviewed PR. Regenerate both references and inspect the stable/development differences.
4. Repeat a clean VSIX installation and first-project startup. Exercise each workflow advertised for the release and
   record editor, Java, extension, server, and source versions in the validation record. Label untested features and
   development-only examples explicitly.
5. Refresh real editor captures only after testing the matching build; keep local image assets and useful alt text.
   Until a verified capture exists, use labeled code examples. Do not present illustrations as editor output.
6. Run frozen installation and `bun run validate`, the repository license checks, and independent complete-diff review.
   Review 360, 768, and 1440 px layouts in both themes, keyboard focus, search, and accessibility findings.
7. After the GitHub Pages deployment succeeds, verify the public homepage, representative guides, search, all legacy
   routes, and `/gvy/404.html`. Record the actual deployment head and unresolved validation limits.

The website workflow watches canonical documentation and the extension manifest so content changes rebuild the site. Its
PR job validates without deploying; the main branch job publishes through the existing Pages environment.

## Build diagnostics

The missing translation collection is fixed with Starlight's `i18nLoader` and English messages. A custom Astro 404 page
uses the supported Starlight page layout with the default 404 route disabled. Astro 7.3.6 fixes its generated MDX
`use astro:head-inject` bundling directive warning. Keep head assets, styles, and scripts verified when upgrading these
dependencies; do not suppress warning categories. The original investigation is
[#1888](https://github.com/albertocavalcante/gvy/issues/1888).
